# Данные Абыла и расчётная модель

Интеграция использует опубликованный набор из main `6de9d59`: 35 вышек, 4200 жалоб, население 12 районов. Источник — `backend/data/`; генератор Абыла — `backend/scripts/generate_demo_data.py`. Исходный набор включён в Git и при запуске не перегенерируется. Резервный генератор Рамазана удалён после появления командных данных.

## Окно анализа

В текущем 60-минутном демонстрационном окне 464 записи: Tower 17 — 347, Tower 23 — 80, Tower 31 — 25, Tower 8 — 12. Эти записи имеют `data_source: synthetic` и `demo_age_minutes`: их относительный возраст намеренно зафиксирован, поэтому сценарий работает и через несколько дней. Журнал анализа явно сообщает об этом. Остальные записи — исторический фон.

Для записей без синтетического относительного возраста используется реальный `timestamp` (или `time`); будущие/невалидные даты исключаются. Счётчик `complaints_count` существующего инцидента — сохранённый агрегат инцидента, не обещание равенства каждому новому временному окну. Например, 128 у INC-1045 не совпадает с 80 текущих жалоб Tower 23. История повторяемости инцидентов — отдельные синтетические исходные данные.

## Формулы Абыла

Все вычисления выполняет Python, AI не меняет числовые результаты.

- `expected_load = current_load_pct / (1 + capacity_increase_pct / 100)`, затем округление для `expected_load_pct`. Предполагаются постоянный спрос и пропорциональный рост ёмкости.
- `improved_fraction = min(1, max(0, current_load_pct - expected_load) / 100 + coverage_increase_pct / 100)`.
- `affected_users_improved = round(affected_users * improved_fraction)`. Это оценка, ограниченная числом затронутых пользователей. Доли от уменьшения нагрузки и роста покрытия считаются непересекающимися; реальное пересечение не моделируется.
- Цена, рост ёмкости/покрытия и сроки берутся из `solutions.json`. Деньги — целые KZT, показатели — проценты.

Контрольный сценарий: Tower 17, нагрузка 96%, 1823 затронутых пользователя. Модернизация за 12 млн даёт округлённый прогноз 71% и оценку улучшения для 600 пользователей. При бюджете 20 млн доступны варианты за 12 и 18 млн; 40 млн недоступен.

Население районов и поиск ближайшей вышки доступны через Python-функции data_service. Число затронутых пользователей у опорных вышек задано синтетически. Модель не учитывает частоты, интерференцию, рельеф или реальные перемещения абонентов. Заказы — сохранённые поручения; выполнение бригадой и измерения после установки не имитируются.
