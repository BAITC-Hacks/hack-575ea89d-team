# Ноутбук 3 — напарник: проверки, демонстрация и защита

## Контекст

Команда на HackAlem делает Beeline Tariff Marketing Campaigns. Старый проект про вышки, карту и жалобы удалён. Два ноутбука владельца: первый — агент/интеграция, второй — данные/гипотезы. Твой ноутбук — независимая проверка, демонстрация результата и подготовка защиты.

Агент получает 23 441 абонента, тестирует гипотезы на пилотах и выбирает 1–10 кампаний «кому → тариф → канал». Цель — прирост выручки минус расходы. 100 000 у.е., 15 000 контактов с пилотами, 5000 на кампанию, 20 пилотов по 10–200. Данные синтетические. Локальная среда не обещает судейский результат.

## Начало

Прочитать AGENTS.md, STATUS.md, README.md, PARTICIPANT_GUIDE.md, docs/API_CONTRACT.md и этот файл. Проверить ветку и чужие изменения. После публикации новой основы:

```bash
git fetch origin
git switch -c work/laptop-3-demo origin/main
```

При существующей ветке продолжить её, не сбрасывать. Установка по README. Запустить проверки baseline и `python tools/report.py --seed 42`.

## Твоя зона

`tools/`, `demo/`, `tests/test_contract*.py`, `tests/test_agent*.py`, `docs/VALIDATION.md`, `docs/PITCH.md`, этот README. Не менять agent.py, strategy/, research/, исходные CSV, официальные evaluator/environment. Изменения зависимостей и общего контракта согласовывать с ноутбуком 1.

## Задачи по приоритету

1. Проверить обязательные требования: запуск, корректные тарифы/каналы, 1–10 финальных кампаний, пилоты >0, реальные ограничения бюджета и охвата с учётом пилотов, повторяемость CSV. В отчёте оценщика число кампаний включает пилоты — не путать с финальным лимитом 10.
2. Провести 10 прогонов и сохранить таблицу min/median/max, число положительных прогонов, длительность. Плохие результаты тоже показывать. Файл `docs/VALIDATION.md` должен содержать фактические команды, окружение и выводы, не обещания.
3. Проверить, что решения меняются при изменении пилотных наблюдений. Граничные сценарии: негативные пилоты, пустой/малый сегмент, остатки бюджета, повторные контакты, недоступная LLM (когда её добавят).
4. Сделать компактную демонстрацию из фактического artifacts/report.json: бюджет, затраты, контакты, пилоты, итоговые кампании, наблюдаемый эффект и результат мока. Можно локальный HTML в demo/ с загрузкой JSON пользователем — без backend и платной инфраструктуры. Интерфейс необязателен для зачёта; сначала проверки и документация.
5. Написать docs/PITCH.md: выступление на 2–3 минуты — проблема → агент → пилоты → план → результат → ограничения. Не описывать LLM/адаптивность как готовые, пока их нет в коде и проверках.
6. Открыть PR своей зоны в main. Ноутбук 1 интегрирует. Не объединять старые ветки про вышки.

## Требования к демо

Все цифры из сохранённого отчёта, seed и режим mock видны. Метрики оценщика доступны только для отчётности, не отдавать их обратно агенту. Показывать финальные кампании отдельно от пилотов. Не выдавать шумное наблюдение за гарантированную прибыль. Ключи и купоны не помещать в браузерный код и репозиторий. Brev/GPU не требуются для первых задач; платный запуск отдельно обсуждается владельцем.

## Готово, когда

Проверки воспроизводятся с чистой установки, README твоей части описывает использование отчёта/демо, защита опирается на реальные результаты, PR не содержит изменений чужих модулей.
